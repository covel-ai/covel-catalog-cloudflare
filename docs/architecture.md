# Architecture and invariants

This repository owns a Workers HTTP entry, D1 persistence, private R2 transport and a trusted Actions runner. Business rules, schemas, adapters, immutable package hashes, release detection and ZIP creation come from the complete, pinned `@covel/catalog-kit` manifest. No Node SQLite or filesystem module is bundled into the Worker; Node 26 runs the collector and packager in Actions.

## Storage and publication

The ingestion protocol is `POST /admin/snapshots/{kind}` with a bounded manifest, then `/{snapshotId}/records/{sequence}`, then `/{snapshotId}/finish`. A record is one entry, release or issue. Each request is at most 32 KiB; large catalogs are never a D1 row or a Worker JSON request. The manifest authenticates ordered records with a rolling SHA-256 chain. Entries precede releases so each release is validated against its current membership. Distinct keys, sequence, kind, counts and final chain are checked. A payload-derived publication ID survives an interrupted upload even if a resumed collector's envelope generation time changes. The first accepted envelope time is retained.

A kind-scoped D1 lease and a conditional sequence guard protect each transactional batch. Staged revisions, observations, tag bindings and entries remain invisible. Completion atomically inserts new ledger records, closes replaced membership intervals, publishes the snapshot and switches the current pointer. The other kind and independently published policy are untouched. Expired/failed staging never replaces the old snapshot. A lease takeover cannot publish against another base snapshot.

Index rows carry start/end generations. Unchanged metadata reuses its row and FTS index across publications; changed metadata, frozen counters and membership exits get new intervals. `fetchedAt` on a reused row remains the time that identical metadata was stored, while envelope generation and source observations are separate. Historical revisions, artifact mappings, tag bindings and counters are retained. Publication writes O(n) small membership/checkpoint records, but does not rewrite every full entry/index or duplicate unchanged revisions. This is still real D1 write usage, not an unlimited free ingest mechanism.

Browse queries use kind/sort indexes and keyset cursors. Search intersects indexed Unicode character grams, then verifies substring matches and uses the canonical relevance score. This preserves short Chinese searches without scanning all JSON. Aggregates are cached by snapshot/query/policy/artifact epoch. The first aggregate computation reads matching database rows; warm pages read summaries from indexes. There is no full-directory transfer or filtering in Worker memory. Name order is normalized binary order in D1; cursors bind this adapter's query version and cannot be exchanged with the Node backend. Both use the same fields, filters and stable tie-break identity.

## Transactions and time

D1 `batch()` is the transaction boundary. Conditional guard statements abort the entire batch when a sequence, lease, snapshot or policy changes. A unique request key and a database trigger create the ticket and increment its counter in the same transaction. Polling pending tasks, Range, HEAD and repeated ticket use never increment a counter. Request-key bindings also reject using a pending key for another revision. Tickets expire after 15 minutes; cursors after 30 minutes. Expired request keys require a new user request key.

A unique job ID includes numeric repository identity, kind, package path, exact commit and packager version. A partial unique index serializes collection of each kind. Claims atomically assign a hashed bearer lease, attempts and expiry. Heartbeats extend a two-minute lease; every completion/upload path verifies current ownership. Failed transient work retries with bounded backoff, up to five attempts; an operator can requeue an exhausted task. A stale runner cannot publish or attach an artifact. It may leave an unreferenced, checksum-addressed object, which is never downloadable without an artifact mapping and ticket.

GitHub requests reserve one D1 gate across both Workers and runners. Its hourly budget, active lease and retry/reset cooldown survive isolates and process restarts. A request expires after 30 seconds before its 45-second gate lease can be reclaimed. Responses are released only after body consumption/cancellation. The configured ceiling is shared even if Actions uses its own restricted GitHub token. Public visibility and numeric owner/repository identity are checked before ticket issuance and every file request, including HEAD and Range. GitHub unavailability or exhausted budget fails closed.

## Private bytes and trust

Actions executes only this repository's checked-in runner and the fixed public kit. Package files are read as data; no `npm install`, build hook, shell command or source script from a package is executed. The canonical packager validates the tree, each blob, portable paths, package import layout and byte limits, then computes content and ZIP hashes. A selected directory becomes ZIP root. A repository ZIP is never substituted.

The runner claim credential cannot publish policy. Its short-lived job credential can access only that job's kind/checkpoints/publication or artifact result. ZIP uploads are streamed through the Worker with an expected SHA-256; R2 performs checksum verification. The Worker never buffers a 200 MiB source package or ZIP for hashing. Private objects include their validated checksum metadata and are checked before streaming. Artifact reservations cap total accepted ZIP storage at 8,388,608,000 bytes by default; failed uploads count conservatively until reviewed cleanup. R2 public access, `r2.dev`, custom bucket domains and public presigned links must remain disabled.

Current policy is applied to list, detail, history, update checks, ticket issuance and redemption. Cached and old artifacts are included. A newer policy invalidates old cursors; existing tickets are rechecked. Artifact hashes become visible to policy only after verified bytes exist. Expired/missing policy disables public catalog operations. Already transferred bytes and direct upstream GitHub URLs are outside this service's control.

## Deployment-specific bounds

100 active policy rules; 32 KiB per metadata record; 32 MiB per resumable checkpoint; 50 queued/running tasks; 2,000 files / 200 MiB unpacked / 20 MiB ZIP from the canonical packager. Exceeding a limit is explicit failure, never silent truncation. Policy growth or a larger directory needs a reviewed limit/storage design and quota measurements. Record bodies and policy rules are intentionally small to fit the free Worker CPU target. Local wall-time tests do not certify Cloudflare production CPU limits.
